# Backend API Integration

This app is a pure consumer of the `AIFinancial` backend's REST API. The
authoritative contract lives in that repo's
`specs/architecture/api-reference.md` — this file documents only the subset
this app uses and the mobile-specific handling around it. If the backend
contract changes, this file is updated by hand; there is no generated
client shared between the two repos.

## Endpoints this app consumes

| Endpoint | Used for |
|---|---|
| `POST /api/devices/pair-code` | N/A — generated by the **web app**, not this app. This app only scans the resulting QR code. |
| `POST /api/devices/redeem` | Pairing: exchanges the scanned code for a device-scoped access + refresh token pair. The one unauthenticated call this app makes. |
| `POST /api/auth/refresh` | Silent token rotation, via an OkHttp `Authenticator` — see `overview.md`. |
| `POST /api/documents` | Draining the offline queue: one call per `QUEUED` row. |
| `GET /api/documents` / `GET /api/documents/{id}` | Populating the local read cache (Stage 2). |
| `GET /api/transactions`, `GET /api/budgets` | Read-only offline cache (Stage 2). |
| `DELETE /api/devices/{id}` | Unlinking this device from Settings (calls the *web app's* endpoint on this device's own id, surfaced as "unlink this device" in the mobile app's own settings screen). |

## Pairing flow (client side)

1. User opens "Link this device" → camera opens in QR-scan mode.
2. Decoded string is the raw pairing code (the same value the web app shows
   as both a QR image and plain text — see `AIFinancial`'s
   `specs/features/mobile-companion-integration.md`).
3. App calls `POST /api/devices/redeem` with `{ code, deviceName, deviceType: "android" }`.
4. On success: store the returned access + refresh token via
   `EncryptedSharedPreferences`; navigate to the main app.
5. On `400` (the backend's deliberately generic "invalid or expired" — see
   that repo's information-hiding design for this exact endpoint): show one
   generic message ("Code expired or already used — generate a new one in
   the web app") and let the user rescan. Never try to guess *why* it
   failed from the client — the backend will not tell you, by design.

## Token refresh (client side)

Implemented once, as an OkHttp `Authenticator`, not scattered across call
sites:

1. A request comes back `401`.
2. Call `POST /api/auth/refresh` with the stored refresh token.
3. On success: persist the **new** access + refresh token (the backend
   rotates on every use — the old refresh token is now dead, per that
   repo's `RefreshTokenCommandHandler`) and retry the original request once.
4. On failure (device revoked, refresh token itself expired/already
   rotated): clear local tokens and force re-pairing. This is the expected,
   correct behavior if a supervisor/account owner revoked this device from
   the web app's Settings page — the next request after that revocation is
   where this app finds out, by design (Stage 19's revocation is enforced
   live, per-request, on the backend; this app has no way to know sooner,
   and must not try to cache or predict revocation state itself).

## What never gets cached locally

Nothing from `/api/auth/*` or `/api/devices/*` beyond the current token
pair. No document content is cached beyond what the user captured on this
device and its own upload status — this app is not a general offline mirror
of the account's full document history (Stage 2 defines the bounded,
explicit read-cache scope; it is not "cache everything the user has ever
looked at").
